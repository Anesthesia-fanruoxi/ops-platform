# 多仓库模板设计（独立链路）

> 分支：`main` 工作区直接开发；单仓流程模板逻辑一行不改。
> 目标：一个项目多个 Git 仓库，每个仓库有自己的 pom/编译命令/产物，不能用一套固定配置套。

## 1. 为什么独立

单仓项目的隐含前提是「项目 = 一个 Git 地址 = 一套编译配置」，`cicd_flow_templates.configs` 就是按这个前提设计的。
多仓项目里每个仓库的 pom 位置、编译命令、产物路径都不同，硬塞进模板会把单仓字段变成误导，所以在数据、页面、构建入口上都单独一条链路。

## 2. 数据模型

| 表 | 说明 |
| --- | --- |
| `cicd_multi_templates` | 一个项目一份多仓库模板（`project_id` 唯一） |
| `cicd_multi_items` | 模板里的仓库行：Git 地址/凭据/语言/编译镜像/编译命令/构建目录/产物路径/Dockerfile |
| `cicd_multi_services` | 仓库产出的服务：服务名/产物目录/jar/jvm，可后补 |

单仓的 `cicd_flow_templates`、`cicd_builds` 结构不变；多仓构建把 `build_mode=multi`、`repo_name`、`services` 写进构建快照，不改表。

## 3. 页面

CI/CD → **多仓库模板**（新增独立 tab，单仓「流程模板」页不动）。

编辑弹窗把前四步合并成一张仓库表格，一行一个仓库：

| 列 | 说明 |
| --- | --- |
| 仓库名 | 参与镜像名/构建记录，项目内唯一 |
| Git 地址 / 凭据 | 每个仓独立 |
| 语言 / 编译镜像 / 编译命令 | 每个仓独立，不共用 |
| 构建目录 | pom 所在目录，`.` = 仓库根 |
| 产物路径 | 相对构建目录，如 `target/*.jar` |
| Dockerfile | 每个仓可选不同模板 |
| 服务 | 批量粘贴：`服务名\|产物目录\|jar名\|jvm`，可先不配 |

## 4. 构建入口（代码分支）

`build_service.trigger_build(..., multi_item_id=None)` 顶部加一个判断：

```python
if multi_item_id:
    from ...multi_repo_service import trigger_item_build
    return trigger_item_build(multi_item_id, environment_id, branch, triggered_by)
# 下面是原来的单仓逻辑，完全不变
```

多仓 `trigger_item_build`：

- 只构建选中的那一个仓库；
- `build_command` 前加 `cd {build_dir} &&`（构建目录不是 `.` 时）；
- 服务映射以 `services: [{name, dir, jar_name}]` 写进快照，Agent 按服务名落盘/命名镜像；
- 没配服务时兜底用仓库名出一个镜像；
- 工作目录、镜像命名空间、端口、环境锁仍按「项目+环境」，与单仓一致。

Agent 侧只多了一个可选的 `steps.services`；单仓不传，行为不变。

## 5. 暂未做

- 多仓构建成功后**不自动部署**（`auto_deploy` 检测 `build_mode=multi` 直接跳过并记日志），避免按目录名误发 YAML；部署口径（服务名 → YAML 文件）下一步再做。
- 多仓构建进度还没有独立列表，先通过构建记录/环境页查看。
- 服务配置目前挂在模板行的弹窗里，可后补；后续可提成项目级「服务配置」页。
