# 统一鉴权中心设计

> **状态：已过时（仅作早期探索记录）**——实际落地为独立 Go 项目 **authPlatform**
> （`D:\project\go\authPlatform`，规格 `authPlatform设计规格.md`、接口 `doc/API.md`），
> 采用「平台代理校验」模式：登录页在各平台、平台转发凭证→authPlatform 验 HMAC 签名→
> 签发不透明 token（不吊销）；本平台的对接实现见 `modules/system/auth_platform.py`、
> `auth_api.py`（登录）、`user_api.py`（用户同步/资料变更转发）。
> 本文档的方案 A/B（统一账号源 → 真 SSO）与授权码跳转式登录已被上述实现取代，仅保留演进背景。
> 目标读者：ops-platform 与 CMDB 平台维护者
> 关联系统：ops-platform（本仓库）、CMDB 平台（线上鉴权，独立系统）

## 1. 背景与目标

### 1.1 现状

- **CMDB 平台**：用于线上环境维护鉴权，已有一套账号体系（线上使用）。
- **ops-platform**：偏测试/本地环境使用，**认证完全自包含**——本地 `users` 表存密码、登录发不透明 token 存 Redis、`security.py` 每次请求校验并滑动续期（详见 §3）。
- 两套系统各自维护账号，导致：一套密码记两处、账号增删改要重复操作、改密/禁用不同步。

### 1.2 目标

1. **一套账号**：账号密码只在一个地方维护，所有系统共用。
2. **单点登录（SSO）**：登录一次，可访问接入的所有系统（目标态，可分阶段达成）。
3. **最小侵入**：不破坏各系统已有的权限模型与业务逻辑；ops-platform 的角色/权限体系保留。

### 1.3 非目标

- 不做权限统一：鉴权中心只回答「你是谁」，不回答「你能干什么」。
- 不引入 AD 域 / Kerberos（本设计不需要域控生态，见 §4.2）。
- 不迁移现有历史密码（统一后由鉴权中心接管，各系统本地密码字段废弃或仅作逃生通道）。

## 2. 总体架构

```
                    ┌─────────────────────────────┐
                    │        统一鉴权中心 (IdP)      │
                    │  - 账号库（唯一身份源）          │
                    │  - 登录页 + 登录会话             │
                    │  - 签发 / 校验 全局 token       │
                    └───────────┬─────────────────┘
                                │ ① 登录（账号密码）
                     ┌──────────▼──────────┐
                     │  浏览器（用户）        │
                     └──────────┬──────────┘
          ┌──────────┬──────────┼──────────┬──────────┐
          ▼          ▼          ▼          ▼          ▼
   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ops-platform│ │  CMDB    │ │  其他系统  │ │  ...     │
   │ (本仓库)   │ │  平台     │ │   (可扩展) │ │          │
   └──────────┘ └──────────┘ └──────────┘ └──────────┘
        每个系统：本地「用户资料 + 角色映射」 + 统一认证接入
```

### 2.1 核心分层原则

| 层 | 归属 | 职责 |
|---|---|---|
| 身份认证（Authentication） | 鉴权中心 | 账号、密码、登录、签发/吊销 token |
| 会话票据（Session Ticket） | 鉴权中心签发 + 各系统消费 | 全局 token 的校验 |
| 授权（Authorization） | **各系统本地** | 角色、权限码、菜单可见性（ops-platform 现有 RBAC 保留） |
| 用户资料（Profile） | 各系统本地 + 鉴权中心映射 | 昵称、邮箱等，可定期同步或首次登录写入 |

> 一句话：**鉴权中心管「你是谁」，各系统管「你能干什么」。**

## 3. ops-platform 现状（改造基线）

| 文件 | 现状 | 统一后角色 |
|---|---|---|
| `modules/system/auth_api.py::login` | 本地 `users` 表 + `check_password_hash` 验密码 → 发随机 token | 改为「从鉴权中心换取身份」；本地不再验密码 |
| `modules/system/session_cache.py` | Redis 存 `auth:token:{token}`（用户+角色+权限快照），滑动续期，用户→token 索引，登录限流 | **保留不动**（会话机制与统一鉴权解耦） |
| `core/security.py::init_auth` | `before_request` 拦截 `/api/`，Bearer/query token → 读 Redis 构造 `g.current_user` | **保留不动**（token 来源与校验逻辑不变） |
| `modules/system/models.py::User` | 本地账号表 | 增加身份映射字段（§6.1），密码字段废弃 |
| `modules/system/role_api.py` / `permissions.py` | 角色权限管理 | 保留不动 |

**关键结论**：ops-platform 的「会话层」与「身份来源」本来就是解耦的（登录写 Redis 会话，鉴权读 Redis 会话）。统一鉴权只需替换「身份从哪来」这一环，`session_cache` 与 `security` 两个核心文件可以零改动。这是本设计可行性高的根本原因。

## 4. 方案选型

### 4.1 三方案对比

| 方案 | 效果 | 成本 | 适用 |
|---|---|---|---|
| **A. 统一账号源** | 一套账号，各系统仍分别登录 | 低（只改登录校验来源 + 用户映射） | 快速见效，先决条件 |
| **B. 真 SSO 鉴权中心** | 登录一次全系统可访问 | 中（新增服务 + 各系统接入跳转） | 目标态 |
| **C. 现成 IdP（Keycloak 等）** | 标准 OIDC/SAML | 中高（多一个运维组件） | 系统数量多、要求标准协议时 |

**决策**：分两阶段演进，A → B，同一套数据模型兼容，不返工（见 §8）。

### 4.2 为什么不搭 AD 域

AD 是目录服务 + Kerberos 域控生态，适合 Windows 域环境做机器/账号统一管理；本场景是两个内网 Web 系统要共享账号，自建鉴权中心（CAS/Keycloak 模式）或对接现有账号库更轻、更贴合。AD/LDAP 可以在未来作为**鉴权中心的账号源**接入（如果 CMDB 本身就是 LDAP 体系），但不必为了统一账号而引入域控。

### 4.3 Token 风格：不透明 token（延续现状）

- 沿用 ops-platform 现有「随机字符串 + Redis 会话」模式，**不引入 JWT**。
- 理由：可即时吊销（改密/禁用即失效）、不携带敏感信息、内网无跨服务验签需求；与现有 `session_cache` 一致，改造最小。
- 全局 token 与本地会话的关系见 §5.2。

## 5. 鉴权中心 API 协议（阶段二目标协议）

> 阶段一（账号源统一）不需要下列接口，仅需 CMDB 提供一个「验密码」入口（§5.3）。
> 以下协议为**建议稿**，具体路径/字段以 CMDB 现状评审后为准【待确认】。

### 5.1 约定

- 统一响应：`{"code": 0, "msg": "ok", "data": {...}}`，非 0 为业务错误；HTTP 状态码用于传输层错误。
- 鉴权中心与各系统后端之间的调用走服务端到服务端（**带服务密钥鉴权**，防伪造），密钥由鉴权中心下发。

### 5.2 登录流程（授权码式，跨域友好）

```
浏览器 → ops-platform 未登录 → 302 跳转 鉴权中心/login?service=<ops回调地址>
鉴权中心 → 用户输入账号密码 → 校验通过 → 302 回 service?ticket=<一次性票据>
ops-platform 后端 → POST 鉴权中心/api/sso/validate {ticket, service} （服务端调用，带服务密钥）
鉴权中心 → {code:0, data:{uid, username, nickname, ...}}  （票据一次性，5分钟内有效）
ops-platform → 本地映射/创建用户 → 写本地 Redis 会话（现有机制）→ 后续请求走现有鉴权
```

**双 token 模型（重要）**：
- **全局 token（IdP 侧）**：用户在鉴权中心的登录态（Cookie 或 token），用于「访问任意接入系统免登录」；登出时由鉴权中心统一吊销。
- **本地会话 token（各系统侧）**：ops-platform 自己发的 Redis 会话，`session_cache` 现有机制，负责本地权限与滑动续期。
- 简化版（可选）：若接入系统都信任鉴权中心全局 token，ops-platform 的 `security.py` 可直接校验全局 token（调鉴权中心 `/api/sso/verify`），跳过本地 Redis 会话；但会丢失本地滑动续期与权限快照优势，**不推荐**，默认走双 token。

### 5.3 接口清单

| 接口 | 方法 | 说明 | 鉴权 |
|---|---|---|---|
| `/api/sso/login` | GET | 登录页入口，`service` 参数为回调地址 | 无 |
| `/api/sso/validate` | POST | 换票：`{ticket, service}` → 用户身份 | 服务密钥 |
| `/api/sso/verify` | POST | 校验全局 token：`{token}` → 用户身份/过期 | 服务密钥 |
| `/api/sso/logout` | POST | 全局登出，吊销 token | 服务密钥 |
| `/api/users/me` | GET | 查询账号信息（供各系统同步资料） | 服务密钥 |
| `/api/auth/verify-credentials` | POST | **阶段一用**：`{username, password}` → 是否有效（不返回密码） | 服务密钥（或限流） |

### 5.4 错误码（建议）

| code | 含义 |
|---|---|
| 0 | 成功 |
| 1001 | 票据无效/已过期 |
| 1002 | 全局 token 无效/过期 |
| 1003 | 账号或密码错误 |
| 1004 | 账号被禁用 |
| 1005 | 登录尝试过多，已锁定 |
| 2001 | 服务密钥无效（调用方未授权） |

## 6. 数据模型与映射

### 6.1 ops-platform `users` 表改造（向后兼容）

| 字段 | 说明 |
|---|---|
| `username` | 保留；与统一账号名一致（映射键） |
| `password_hash` | **废弃**（统一后不再校验；保留仅作逃生通道/迁移期，见 §7.3） |
| `auth_source`（新） | `local`（默认，现有数据）/ `sso`（统一接入） |
| `auth_uid`（新） | 鉴权中心账号唯一 ID（`auth_source='sso'` 时必填，唯一索引） |

### 6.2 首次登录自动映射

```
鉴权中心返回 {uid, username, nickname}
  → users 表查 auth_uid = uid
     命中 → 更新昵称等资料，继续
     未命中 → 查 username 是否被本地旧账号占用
        未占用 → 新建 User(auth_source='sso', auth_uid=uid, 默认角色=普通用户)
        已占用（历史本地账号）→ 绑定：auth_source='sso', auth_uid=uid，沿用原角色与权限
```

> 历史本地账号与统一账号重名时自动绑定，避免重复建号；绑定结果可在「系统管理→用户」中人工调整角色。

### 6.3 角色与权限

- 角色分配仍由 ops-platform 管理员在本地完成（新账号默认分配「普通用户」角色，管理员可提升）。
- 不做角色同步到鉴权中心；如未来多系统需要统一角色，再评估单独的角色服务（超出本设计范围）。

## 7. 安全与运维要求

1. **HTTPS 必须**：账号密码与 token 全程加密传输；鉴权中心为最高信任边界，禁止明文 HTTP。
2. **登录限流与锁定**：鉴权中心实现失败次数锁定（参考 ops-platform `session_cache` 现有 5 次/15 分钟逻辑）。
3. **票据一次性**：`ticket` 5 分钟有效、用后即焚，防重放。
4. **服务密钥**：各系统调用鉴权中心接口必须带服务密钥（随机长串），密钥泄露即轮换。
5. **吊销链路**：改密/禁用/删号 → 鉴权中心吊销全局 token → 各系统本地会话由「用户→token 索引」批量失效（ops-platform `delete_user_sessions` 已具备）。
6. **防 CSRF**：登录页与回调按 OAuth2/CAS 惯例校验 `state`/`service` 参数与来源。
7. **单点登出（SLO，可选）**：首版可只做「登出本系统 + 调鉴权中心登出」，后续再扩展广播登出。
8. **审计**：鉴权中心记录登录成功/失败/登出日志，各系统保留操作日志现状不变。

## 8. 实施计划

### 阶段一：统一账号源（低风险，先做）

| # | 任务 | 涉及 |
|---|---|---|
| 1 | 确认 CMDB 账号校验入口（REST API / LDAP / 直连库）【待确认】 | CMDB |
| 2 | `users` 表加 `auth_source` / `auth_uid` 字段（bootstrap 自动迁移） | ops-platform |
| 3 | `auth_api.login` 改为「调 CMDB 验密码 → 映射/创建本地用户 → 写本地会话」；本地密码校验仅保留给 `auth_source='local'` 的存量账号 | ops-platform |
| 4 | 前端登录页不变；失败提示语统一 | ops-platform |
| 5 | 验证：CMDB 账号可登录 ops-platform；存量本地账号仍可登录（迁移期） | 联调 |

**阶段一完成即达成「一套账号」，两系统仍分别登录。**

### 阶段二：真 SSO 鉴权中心

| # | 任务 | 涉及 |
|---|---|---|
| 6 | 新建鉴权中心服务（或复用 CMDB 扩展），实现 §5 协议 | 鉴权中心 |
| 7 | ops-platform 登录改跳转 + 回调换票（§5.2 双 token 模型） | ops-platform |
| 8 | CMDB 接入同一鉴权中心 | CMDB |
| 9 | 单点登出、服务密钥轮换、监控告警 | 全部 |

### 风险与回退

- **CMDB 不可用**：阶段一登录失败时，保留 `auth_source='local'` 管理员账号作为**逃生通道**（配置开关），业务不中断。
- **鉴权中心不可用**：阶段二同理——各系统保留本地逃生账号；鉴权中心恢复后自动恢复。
- **回退**：改 `auth_source` 与开关即可回退到本地认证，数据不迁移、不破坏。
